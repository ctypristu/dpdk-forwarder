# dpdk-forwarder 设计文档

版本 V1.0 ｜ 2026-09-17

---

## 一、总体架构

系统是一个单进程、多阶段的用户态转发器，采用**快慢路径分流**模型：

```
                    ┌──────────────────────────────────────┐
                    │             收包 (PMD)                │
                    └──────────────────┬───────────────────┘
                                       ▼
                    ┌──────────────────────────────────────┐
                    │   解析：以太网 → IPv4 → TCP/UDP       │
                    └──────────────────┬───────────────────┘
                                       ▼
                    ┌──────────────────────────────────────┐
                    │         查询会话表（快路径）            │
                    └───────┬──────────────────────┬───────┘
                          命中                    未命中
                            │                      │
                            │                      ▼
                            │      ┌───────────────────────────┐
                            │      │  查询 ACL 规则表（慢路径）  │
                            │      └──────────────┬────────────┘
                            │                     ▼
                            │      ┌───────────────────────────┐
                            │      │      建立会话记录          │
                            │      └──────────────┬────────────┘
                            │                     │
                            └──────────┬──────────┘
                                       ▼
                    ┌──────────────────────────────────────┐
                    │   执行动作：放行（转发）或丢弃          │
                    └──────────────────┬───────────────────┘
                                       ▼
                    ┌──────────────────────────────────────┐
                    │   转发：查 MAC 表 → 单播发送 / 泛洪    │
                    └──────────────────────────────────────┘
```

核心思想：**一条连接上只有首包需要做完整判断，后续包直接复用首包的结论。**

## 二、模块划分

| 模块 | 文件 | 职责 |
|---|---|---|
| 端口 | `port.h/cpp` | DPDK 端口的配置、启动、收发、信息打印 |
| 解析 | `packet.h/cpp` | 以太网 / IPv4 / TCP / UDP 头部解析 |
| 二层转发 | `mac_table.h/cpp` | MAC 地址学习、查表、老化 |
| 策略 | `acl.h/cpp` | 五元组规则表与匹配 |
| 会话 | `session.h/cpp` | 会话建立、命中、计数、老化 |
| 主程序 | `main.cpp` | 初始化、主循环、动作执行、统计输出 |

模块之间只通过头文件里的接口交互，没有全局状态，便于单独测试和后续替换。

## 三、关键数据结构与选型理由

### 3.1 五元组与双向规范化

```cpp
struct FiveTuple {
    uint32_t src_ip, dst_ip;
    uint16_t src_port, dst_port;
    uint8_t  proto;
};
```

所有字段以**主机字节序**存储。网络字节序的数据在解析阶段就转换好了，
后续比较和哈希都不用再转，少一层容易出错的地方。

**关键设计：`canonical()` 双向规范化。**

一条 TCP 连接的两个方向，五元组是不同的：

```
方向 A：192.168.1.10:52341 → 10.0.0.1:80
方向 B：10.0.0.1:80 → 192.168.1.10:52341
```

如果直接用原始五元组做 key，这两个方向会落到两条记录上，内存翻倍，
而且状态还要双向同步。

`canonical()` 的做法是按 (IP, 端口) 排序，让较小的那个作为"源"。
这样两个方向映射到同一个 key，会话表只需要一条记录，也不存在同步问题。

代价是：**从会话记录里看不出谁先发起**。如果业务需要区分发起方向，
得额外存一个标记位。当前版本不需要，所以没做。

### 3.2 MAC 表：开放寻址 + 线性探查

```cpp
static constexpr uint32_t kCapacity = 4096;
struct Entry { rte_ether_addr mac; uint16_t port_id; uint64_t updated_at; bool valid; };
Entry entries_[kCapacity];
```

**为什么不用 DPDK 的 rte_hash？**

| | 开放寻址数组 | rte_hash |
|---|---|---|
| 内存 | 固定 4096 × 24B ≈ 96KB | 动态分配，额外索引开销 |
| 查找 | 一次哈希 + 少量探查 | 一次哈希 + bucket 内比较 |
| 容量上限 | 固定，满了插不进 | 可配置，满了两倍扩容 |
| 适用场景 | 条目数可控、追求确定性 | 条目数不可预测 |

MAC 表的条目数在真实网络里是有界的（一个二层域内的设备数量），
4096 条足够，而且**固定容量的好处是内存占用可预测、不会有运行时扩容抖动**。
在 DPDK 这种对确定性要求高的场景里，这是有价值的取舍。

表满时的行为是**停止插入**而不是覆盖或报错——已有条目继续服务，
新条目等老化腾出空间。这样不会因为表满而破坏已有的转发关系。

哈希用 FNV-1a：实现只有几行，对 6 字节输入分布足够均匀。

### 3.3 ACL 表：rte_hash 精确匹配

```cpp
rte_hash* hash_;   // key = FiveTuple, value = AclAction
```

**为什么这里反而用 rte_hash？**

和 MAC 表相反——ACL 规则的数量由用户配置决定，可能几千也可能几十万，
无法预先确定容量。rte_hash 支持动态配置容量、查找 O(1)，
而且是 DPDK 生态里的标准组件，稳定性和性能都经过验证。

**动作的存储方式**：`AclAction` 只有两个取值，用一个字节就够了。
与其为每条规则分配一块内存存 action，不如直接把它编码进 `void*`：

```cpp
void* data = reinterpret_cast<void*>(static_cast<uintptr_t>(action));
rte_hash_add_key_data(hash_, &tuple, data);
```

省掉了每条规则一次 `malloc`，查找时也不用解引用指针。

**当前限制**：只支持精确五元组匹配，**不支持掩码通配**（比如"整个 10.0.0.0/8"）。
通配匹配需要用另外的算法，见第六节。

### 3.4 会话表：rte_hash + 定期老化

```cpp
struct SessionEntry {
    FiveTuple key;          // 规范化后的 key
    AclAction action;
    uint64_t last_seen;     // 秒
    uint64_t pkts;
    uint64_t bytes;
};
```

会话条目本身用 `new` 分配，哈希表里存指针。为什么不做成内联数组？
因为会话长度参差不齐，而且老化时逐个释放更直接。

**老化的实现有个坑**：`rte_hash_iterate` **不允许在遍历过程中修改哈希表**。
所以实现是两阶段：

```cpp
// 阶段一：遍历，把过期的 key 收集到栈上数组
while (rte_hash_iterate(hash_, &key, &data, &iter) >= 0) {
    if (expired(entry)) expired_keys[n++] = entry->key;
}
// 阶段二：统一删除
for (i in expired_keys) { delete entry; rte_hash_del_key(hash_, &key); }
```

单轮最多收集 4096 条（`kMaxRemovePerRound`），避免一次老化占用太长时间
影响转发。剩下的一分钟后再处理。

## 四、报文处理流程

### 4.1 分支判断

```
解析失败（报文太短）           → 丢弃
非 IPv4（ARP / IPv6）          → 不做 ACL，直接二层转发
IPv4 且是 TCP/UDP              → 完整五元组参与 ACL 匹配
IPv4 但是 ICMP 等无端口协议     → 端口字段留 0 参与匹配
```

**这里有个曾经踩过的坑**：最初的条件写成"非 IPv4 或非 TCP/UDP 就跳过 ACL"，
结果 ICMP 报文全部绕过了策略。修正是把判断收窄为**只排除非 IPv4**——
ICMP 没有端口，但它同样是应该受策略管的流量。

### 4.2 动作执行

| 动作 | 行为 |
|---|---|
| `kDrop` | 释放 mbuf，计数 +1 |
| `kPass` | 走二层转发：查 MAC 表 → 单播发送 / 泛洪 |

**注意顺序**：源 MAC 的学习在 ACL 判断**之前**完成。也就是说，
即使一个包会被策略拒绝，它的源地址依然会被学习。

这是有意的，和真实交换机的行为一致：MAC 学习是二层的事，
安全策略是三层以上的事，两者互不干扰。如果需要"被拒绝的源不学习"，
那是另一种设计取向（防地址欺骗），当前版本没做。

## 五、内存管理

### 5.1 mbuf 生命周期

接收方向：mbuf 由 mempool 提供，在 `rx_burst` 时取走。

之后每个包只有两条路：

1. **被发送** —— `tx_burst` 成功，mbuf 的所有权交给网卡驱动，发送完成后由驱动归还 mempool
2. **被丢弃** —— 显式 `rte_pktmbuf_free` 归还

**没有第三条路**。这是必须保证的不变量，任何一条分支漏了释放，
长时间运行都会耗尽 mempool 导致丢包。

### 5.2 泛洪时的 mbuf 复制

泛洪需要往多个端口发同一个包。做法是：

- 前面 n-1 个端口：用 `rte_pktmbuf_clone` 复制（共享数据区，只复制元数据）
- 最后一个端口：直接用原 mbuf

`clone` 是浅拷贝——不复制报文内容，只新建一个 mbuf 头部指向同一块数据。
对于泛洪这种"内容完全相同"的场景，这是最省的做法。

## 六、已知限制与后续改进

### 6.1 当前限制

| 限制 | 影响 |
|---|---|
| ACL 不支持掩码通配 | 无法用一条规则覆盖一个网段 |
| 单核处理 | 没有利用多核，性能上限受单核限制 |
| 分包链未处理 | 解析只假设报文在连续内存里（`m->data_len`），大于 MTU 的巨帧会解析失败 |
| 会话表无持久化 | 进程重启后会话全部丢失 |
| 没有 ICMP 错误处理 | 不支持分片、TTL 超时等需要回 ICMP 的场景 |

### 6.2 改进方向

**掩码通配的 ACL**：标准做法是 tuple space search——按"哪些字段是通配的"
把规则分组，每组一个哈希表，查找时遍历所有组。组数通常远小于规则数，
所以比线性匹配快得多。

**多核并行**：两个方向——

- **RSS 分流**：网卡按流哈希把包分到不同队列，每个核处理一部分流，核间无共享状态
- **功能分离**：一个核收包、一个核转发，通过无锁环形队列传递

前者更常见，也更容易做对。

**批量处理**：主循环里对每个包单独调用 `tx_burst`，可以改成攒够一批再发。
收益在于摊薄每次访问网卡的固定开销。

## 七、性能相关的设计点小结

按对性能的影响排序，这些是本项目里有明确权衡的地方：

1. **批量收发**（burst=32）——每次访问网卡的开销被 32 个包分摊
2. **会话表前置**——避免每个包都查 ACL，这是数量级的影响
3. **零拷贝**——mbuf 在整条路径上不复制数据，泛洪用 clone 而非 copy
4. **无锁**——每核独立处理，没有锁竞争（当前单核，多核版本会保持这个性质）
5. **大页与 mempool 缓存**——减少 TLB miss 和频繁的池操作

第 2 条是这个项目最有说服力的设计点，实测中 5000 个包只有 1 次 ACL 查询。
